1. Why tensors

Module 1's scalar autodiff is correct — it trains xor end-to-end. But every weight is its own NodeId. A Linear(2, 4) layer has 12 parameters and produces 4 outputs from 2 inputs, which means roughly 20 graph nodes per sample just for that one layer. Scaling to a 28×28 MNIST image with a 784→128 layer would build ~100,000 nodes per sample, and the graph traversal cost dominates everything.

It's also painfully verbose at the call site. Here's the actual Linear.forward from module 1:

Scalar Linear.forward (~50 lines)

pub fn forward(
    &mut self,
    graph: &mut ScalarGraph,
    in_ids: Vec<NodeId>,
) -> Vec<NodeId> {
    let weight_ids: Vec<Vec<NodeId>> = self.weights.iter()
        .map(|row| row.iter().map(|w| graph.add_leaf(*w)).collect())
        .collect();
    let bias_ids: Vec<NodeId> = self.biases.iter()
        .map(|b| graph.add_leaf(*b)).collect();

    let mut output_ids = vec![NodeId(0); self.biases.len()];
    for i in 0..self.biases.len() {
        let mut acc_id = graph.apply(
            ScalarOp::Mul(graph.get_node(in_ids[0]).out,
                          self.weights[i][0]),
            vec![in_ids[0], weight_ids[i][0]],
        );
        for (j, w) in self.weights[i].iter()
                          .enumerate().skip(1) {
            let prod = graph.apply(
                ScalarOp::Mul(graph.get_node(in_ids[j]).out, *w),
                vec![in_ids[j], weight_ids[i][j]],
            );
            acc_id = graph.apply(
                ScalarOp::Add(graph.get_node(acc_id).out,
                              graph.get_node(prod).out),
                vec![acc_id, prod],
            );
        }
        acc_id = graph.apply(
            ScalarOp::Add(graph.get_node(acc_id).out, self.biases[i]),
            vec![acc_id, bias_ids[i]],
        );
        output_ids[i] = acc_id;
    }
    self.weight_ids = Some(weight_ids);
    self.bias_ids = Some(bias_ids);
    output_ids
}

Tensor Linear.forward (the goal)

}

Module 2 builds the machinery to make the right-hand version possible: a multi-dimensional Tensor type with strided storage, broadcasting, an autograd graph that records ops on tensors instead of scalars, and operator overloading so call sites read like math.

What we're not doing yet: rayon parallelism (module 7), GPU (module 8), or replacing our hand-rolled storage with ndarray (deferred to a future FastOps backend). Single-threaded CPU with Vec<f64> for now. The trait-based backend abstraction we set up here is what lets all of that drop in later without rewriting Linear / Network / loss / train.

2. TensorData layout

A tensor is conceptually a multi-dimensional array. Memory is one-dimensional. The bridge is strides: a per-dim multiplier that maps a logical index [i, j, k, ...] to a flat offset:

flat_offset = i * strides[0] + j * strides[1] + k * strides[2] + ...

For a contiguous (3, 4) tensor laid out row-major, the strides are [4, 1] — moving one step in the row dim advances 4 elements in storage, moving one step in the column dim advances 1.

A (3, 4) tensor with row-major strides [4, 1]. Logical 2D indices map to a flat Vec<f64> via the dot product of index and strides.

The struct is small:

pub struct TensorData {
    pub storage:        Rc<Vec<f64>>,
    pub storage_offset: usize,
    pub shape:          Vec<usize>,
    pub strides:        Vec<usize>,
}

Two fields beyond the obvious deserve a note. storage is Rc<Vec<f64>>, not a bare Vec: permutes, broadcasts, slices, and per-batch views in matmul all want to share the same underlying numbers without copying. The COW comes in through set, which calls Rc::make_mut — if the storage has exactly one owner, you write in place; otherwise it clones first so siblings aren't perturbed. storage_offset is the starting index into storage for this view. Without it, a slice into the middle of a larger tensor would need its own Vec. With it, you reuse storage and just bump the offset — every read becomes storage[storage_offset + Σ strides[i]·idx[i]].

The real magic is what stride math enables. Consider transpose: in most array libraries, transposing a large tensor would copy data. With strides, it's metadata-only:

Same storage, transposed logical view. Only the strides flipped from [4, 1] to [1, 4] — zero data copied. This is why x.t() in PyTorch is O(1).

The same principle gives us views (slicing without copying), reshape (also free for contiguous tensors), and broadcasting (which we'll cover in section 3).

Task 2.1 — Implement TensorData

src/tensor_data.rs

What to implement:

impl TensorData {
    pub fn new(storage: Vec<f64>, shape: Vec<usize>) -> Self;

    pub fn zeros(shape: Vec<usize>) -> Self;
    pub fn ones(shape: Vec<usize>) -> Self;

    /// Logical index → flat storage offset using strides.
    pub fn flat_index(&self, idx: &[usize]) -> usize;

    pub fn get(&self, idx: &[usize]) -> f64;
    pub fn set(&mut self, idx: &[usize], val: f64);

    pub fn size(&self) -> usize; // product of shape
    pub fn ndim(&self) -> usize; // shape.len()

    /// New TensorData with axes permuted. Storage unchanged.
    pub fn permute(&self, axes: &[usize]) -> Self;

    /// Iterator over all logical indices in row-major order.
    pub fn iter_indices(&self) -> impl Iterator<Item = Vec<usize>>;

    /// Zero-copy broadcast view. Shape becomes target_shape; strides
    /// get 0 in any dim that was size 1 in self or didn't exist.
    /// Storage is shared via Rc::clone.
    pub fn broadcast_to(&self, target_shape: &[usize]) -> Self;
}

/// Standard row-major strides for a given shape: stride[i] = product of shape[i+1..]
pub fn contiguous_strides(shape: &[usize]) -> Vec<usize>;

/// NumPy-style broadcast output shape. Panics if shapes are not broadcastable.
pub fn broadcast_shape(a: &[usize], b: &[usize]) -> Vec<usize>;

/// Strides for viewing (orig_shape, orig_strides) as if it had target_shape.
/// Original strides are PRESERVED for matching dims; stride 0 for dims being
/// broadcast (size 1 in orig, or didn't exist in orig at all).
pub fn broadcast_strides(
    orig_shape: &[usize],
    orig_strides: &[usize],
    target_shape: &[usize],
) -> Vec<usize>;

Rust notes

  • Slice vs Vec. Take &[usize] as input for indices (more flexible than Vec<usize> at the API). Return Vec<usize> from iter_indices because each yielded index is its own owned thing.
  • permute doesn't move data. Build new shape and strides by permuting the originals with the given axis order. Share the same storage via Rc::clone(&self.storage) — true zero-copy view.
  • Don't validate strides at construction time unless you want to forbid non-contiguous tensors. We do want non-contiguous (transpose, broadcast), so accept any consistent strides.
  • flat_index is the hot path. It's called once per element per op. Resist the urge to add bounds checks beyond what storage[offset] already does via Vec.
  • broadcast_strides needs original strides. Broadcasting doesn't invent new strides — it preserves the original ones for matching dims and substitutes 0 for the dims being broadcast. So the function takes (orig_shape, orig_strides, target_shape), not just (orig_shape, target_shape). Example: source shape=[1, 3], strides=[3, 1], target [4, 3] → broadcast strides [0, 1]. The original stride 3 on dim 0 is irrelevant once that dim becomes broadcast.
  • Don't set on a broadcast view. Multiple logical cells map to the same storage slot (that's the whole point of stride 0). Mutating through a broadcast view has surprising aliasing semantics — and Rc::make_mut would COW first, masking the issue but still leaving you with a view that aliases itself. For autograd-style code this never matters because ops always produce new tensors, but worth a /// note on broadcast_to.

Tests to write (tests/test_tensor_data.rs)

  • new computes correct strides for shapes like [3, 4], [2, 3, 4], [5].
  • get / set round-trip for various multi-dim indices.
  • permute([1, 0]) on a [3, 4] tensor swaps strides; same data accessed differently.
  • iter_indices on [2, 3] yields [0,0], [0,1], [0,2], [1,0], [1,1], [1,2] in order.
  • size for [2, 3, 4] is 24.
  • broadcast_strides: for (orig=[3], strides=[1]) to target [4, 3], returns [0, 1]. For (orig=[4, 1], strides=[1, 1]) to [4, 3], returns [1, 0].
  • broadcast_to shares storage (Rc::ptr_eq on the storage Rc before and after) and produces a view where get returns the expected aliased value for each broadcast index.
  • broadcast_shape([3], [4, 3]) returns [4, 3]; broadcast_shape([2, 4], [3, 4]) panics (not broadcastable).

3. Indexing & broadcasting

Broadcasting is what lets tensor_3 + tensor_4x3 work without manual replication. The rule comes from NumPy:

  1. Align shapes from the right.
  2. Each pair of dims is compatible iff they're equal OR one of them is 1.
  3. If one tensor has fewer dims, it gets implicit 1s on the left.
  4. The output shape is the max of each aligned pair.
a.shape b.shape result.shape compatible?
[3][4, 3][4, 3]yes
[4, 1][1, 3][4, 3]yes
[2, 3][3][2, 3]yes
[4][3]—no
[2, 4][3, 4]—no

The trick: instead of physically replicating the smaller tensor, we set its stride to 0 on the dim being broadcast. A stride of 0 means "no matter how this index advances, stay on the same element."

Broadcasting a + b where a has shape (3,) and b has shape (4, 3). a's stride for the new leading dim is 0, so iterating the output's rows reuses the same 3-element storage four times.

Implementation-wise, broadcasting is a function from (shape_a, shape_b) → (shape_out, strides_a_broadcast, strides_b_broadcast). The original storages aren't touched. The element-wise zip just walks both with their broadcast strides.

Two ways to expose this in the API, and you want both:

  • broadcast_to(target_shape) -> TensorData — a public method on TensorData that materializes a view with the broadcast strides. Storage is shared via Rc::clone; no copies. Useful for explicit broadcasting (e.g., in the backward of broadcast ops, where you need to reduce the gradient back to the original shape) and for testing the stride-0 trick in isolation.
  • Internally inside zip — call a.broadcast_to(&out_shape) and b.broadcast_to(&out_shape), then iterate the common output shape, reading via get on each view. Both views have the same shape, so the iteration is symmetric. The output TensorData built from the result is contiguous (normal strides via TensorData::new).
Worked example: a.broadcast_to(&[4, 3]) when a: shape=[3], strides=[1] 
let offset = 2 - 1;  // target ndim - orig ndim = 1
// j=0 < offset → new dim, stride 0
// j=1, i=0: orig_shape[0]==3, target_shape[1]==3 → keep stride 1
// result: strides=[0, 1]

// the broadcast TensorData:
TensorData {
    storage: Rc::clone(&a.storage),   // shared, 3 elements
    shape:   vec![4, 3],
    strides: vec![0, 1],
}

// shape.iter().product() == 12 > storage.len() == 3 — that's expected.
// get([0,0]), get([1,0]), get([2,0]), get([3,0]) all return storage[0],
// because stride 0 on dim 0 contributes nothing to the flat offset.

Task 2.2 — TensorOps and SimpleOps

src/tensor_ops.rs

This is the trait that abstracts "how to actually do tensor work." A single trait lets you swap in SimpleOps (this module), FastOps (rayon-parallel, module 7), GpuOps (wgpu, module 8), and eventually CudaOps — all without rewriting Linear or the loss functions.

pub trait TensorOps {
    /// Apply a unary function element-wise.
    fn map(input: &TensorData, f: impl Fn(f64) -> f64) -> TensorData;

    /// Apply a binary function element-wise with broadcasting.
    fn zip(
        a: &TensorData,
        b: &TensorData,
        f: impl Fn(f64, f64) -> f64,
    ) -> TensorData;

    /// Reduce along a single dim. `keep_dims` controls whether the
    /// reduced axis collapses (false) or stays as size 1 (true).
    fn reduce(
        input: &TensorData,
        f: impl Fn(f64, f64) -> f64,
        init: f64,
        dim: usize,
        keep_dims: bool,
    ) -> TensorData;

    /// 2D matrix multiply (or batched). Output shape per matmul rules.
    fn matmul(a: &TensorData, b: &TensorData) -> TensorData;
}

pub struct SimpleOps;
impl TensorOps for SimpleOps { /* ... */ }

Three primitives — map, zip, reduce — plus matmul cover the entire surface of element-wise tensor math. Sigmoid is map(sigmoid). Add is zip(|a, b| a + b). Sum-along-dim is reduce(|a, b| a + b, 0.0, dim, keep_dims). Matmul is its own special case because it's not element-wise.

The keep_dims flag on reduce matters more than it looks. With keep_dims=false the reduced axis is removed; with true it stays as size 1. The choice ripples into backward: Tensor::sum uses keep_dims=true under the hood, so its backward arm is a one-line gradient.broadcast_to(&orig_shape) — the size-1 dim expands cleanly to the original size. The keep-dims convention also matches what maybe_reduce_broadcast needs when reducing broadcast dims in Add/Mul backward (it builds size-1 dims, not removes them).

Rust notes

  • Using impl Fn instead of fn pointer. impl Fn(f64) -> f64 lets callers pass closures with captured state (rare but useful) and the compiler can monomorphize + inline.
  • matmul is naive for now. Three nested loops using flat_index. Don't use BLAS or simd. We're not optimizing — the trait abstraction is what lets module 7 do that later without touching this code.
  • Static dispatch on the backend. Make Tensor generic over the backend (Tensor<B: TensorOps>) OR pick one at compile time via a type alias. Generic is more flexible; type alias is simpler. Start with the alias; switch to generic if you actually want to support multiple backends at once.
  • zip implementation pattern. Compute out_shape = broadcast_shape(&a.shape, &b.shape), then let av = a.broadcast_to(&out_shape); and same for b. Now both views have identical shape — iterate via av.iter_indices(), call av.get(&idx) and bv.get(&idx), push f of them into a fresh contiguous output. Three lines of broadcast setup hide all the stride-0 trickery behind a clean iteration.
  • reduce and matmul failure modes. Validate at entry with assert!: reduce wants dim < input.ndim(); matmul wants both 2D with a.shape[1] == b.shape[0]. Panic with a descriptive message, not a silent wrong-shape result. (See the "panic vs Result" decision — we panic on shape errors because they're programmer bugs.)

Tests

  • map(sigmoid) on a small tensor matches per-element sigmoid.
  • zip(+) with broadcasting [3] + [4, 3] produces the (4, 3) sum (verify against hand-computed values).
  • reduce(+, 0.0, dim=0) on [2, 3] gives [3] column sums.
  • matmul of [2, 3] × [3, 4] matches a hand-computed reference. Also test [3, 3] × [3, 1].

4. Tensor wrapper & autograd graph

The Tensor type itself is two pieces glued together: a TensorData (the numbers) and an optional History (the autograd pointer):

pub struct Tensor {
    pub data: Rc<TensorData>,
    pub history: Option<History>,
}

pub struct History {
    pub graph: Rc<RefCell<TensorGraph>>,
    pub node_id: TensorNodeId,
}

history = None means "this tensor is not tracking gradients" — like a constant input or a sample's target label. Setting requires_grad on a leaf creates a History with a fresh graph (or attaches to an existing one when combined with other tensors).

The TensorGraph itself is an arena, just like ScalarGraph was. The key difference: every node's output is a TensorData, not a single f64.

pub struct TensorGraph {
    pub nodes: Vec<TensorNode>,
}

pub struct TensorNode {
    pub op: TensorOp,
    pub out: Rc<TensorData>,
    pub gradient: Option<TensorData>,
    pub parents: Vec<TensorNodeId>,
}

The graph sharing is what closes the ergonomics gap. Three Tensors participating in let c = &a + &b; all hold an Rc clone of the same graph — so the + operator overload can reach into the shared graph and add a new node without any &mut parameter being threaded through the call:

Three Tensors sharing the same Rc<RefCell<TensorGraph>>. Each carries its own node_id but they all reach the same arena. Refcount = 3. When all three go out of scope, the graph drops.
Aside: why Rc<RefCell<>> here is fine (and not the anti-pattern it sometimes is)

Rc<RefCell<>> has a reputation as a Rust smell. The reputation is half-deserved. Most of the time when you reach for it, you're trying to express a Pythonic "everything is a shared, mutable reference" world that Rust's borrow checker is specifically built to disallow. The right fix is usually not to wrap in Rc<RefCell> — it's to restructure ownership (often via an arena + indices, exactly what we already did for the scalar graph).

But there's a narrow set of cases where it is the right tool. The semantics it provides — multiple owners, interior mutability, refcounted lifetime — exactly match certain real-world data structures. The classic example from the Rust book is a graph of nodes that reference each other and need mutation. That's literally our case:

  • Shared ownership. Many Tensors point at the same TensorGraph. The graph's lifetime is "until the last referencing Tensor is dropped." That's refcount semantics.
  • Interior mutability. The graph grows as ops run. We need to mutate it through a shared reference, not an exclusive one (otherwise the operator overload can't take &self).
  • No alternative is cleaner. Bare arena + explicit &mut graph brings back the scalar-API pain we're fixing. unsafe raw pointers manually reimplement refcounting badly. Thread-local current-graph breaks test isolation and has init-order issues.

Real costs (in concrete numbers):

  • Refcount. One atomic-free integer increment/decrement per clone(). ~1 ns. Negligible versus the cost of even the cheapest tensor op.
  • RefCell borrow check. One integer comparison per borrow() or borrow_mut(). ~1 ns. Same story.
  • Panic risk. borrow_mut panics if a borrow is already held. Mitigated by scoping the borrow_mut tight — usually a 1–3 line block inside the op implementation.
  • Not Send. Rc isn't thread-safe. If module 7's rayon parallelism needs to share a graph across threads (it shouldn't — each thread can have its own), we'd upgrade to Arc<RwLock<>>. Single-threaded for now is correct.

What we're NOT doing (the real anti-patterns):

  • Wrapping every struct field in Rc<RefCell> "just in case" — only the autograd graph.
  • Using it to avoid learning lifetimes — we already used a clean arena pattern for scalars; we know the alternative.
  • Sharing primitives that should just be Copy.
  • Hiding all mutation behind it instead of using &mut self where natural — TensorData stays plain.

How this actually shows up in the code: two helper functions in src/tensor.rs — make_unary_op and make_binary_op_ref — own the graph.borrow_mut() calls so individual op implementations stay one-liners. Each helper handles "compute the data, find the shared graph, register parent leaves if needed, call graph.apply(...)." Parent-id lookup is its own Tensor::node_id_in method; graph-conflict resolution is pick_shared_graph. Anyone reading the code can see at a glance that the borrow_mut is scoped to a single op call and never escapes — no nested-borrow surprises possible.

Bottom line: add a /// comment on the History struct saying "this is the deliberate shared-mutable-graph pattern, not a borrow-checker workaround." Then anyone who greps for RefCell in the codebase reads that note and knows it's intentional.

Rust notes

  • Why Rc<TensorData> for the data field? So copying a Tensor (e.g., return-by-value from an op) is cheap — no cloning the underlying Vec<f64>. The graph's TensorNode.out and the Tensor's data can point at the same Rc, sharing storage.
  • Scope the borrow_mut. When applying an op: let id = self.graph.borrow_mut().apply(...); on one line, no longer than that. Don't hold a borrow across other code that might also need the graph.
  • Graph creation rule. If at least one operand has a history, the output has a history pointing to the same graph. If no operand has a history, the output has no history (constant propagation). Decide this in the op impl, not in the user code.
  • requires_grad consumes self. By taking ownership and returning a new Tensor, you avoid the "is this the same tensor or not?" confusion — the caller's old handle is gone.

Tests

  • requires_grad sets up history with a fresh graph and a leaf node.
  • Two tensors that aren't connected (separate requires_grad calls) have separate graphs — verify by comparing Rc::ptr_eq on the graph handles.

5. Operator overloading

This is the moment the API ergonomics flip. Same operation, two worlds:

Scalar (current)

let sum_id = graph.apply(
    ScalarOp::Add(
        graph.get_node(a_id).out,
        graph.get_node(b_id).out,
    ),
    vec![a_id, b_id],
);

Tensor (the goal)

let c = &a + &b;

The implementation pattern for each binary op decomposes into four steps. Every binary op uses the same shape — your job is to write a single helper that captures it, then have each impl call that helper with the right op variant and compute closure:

  1. Compute the output data. Use the corresponding SimpleOps primitive — e.g. SimpleOps::zip(&a.data, &b.data, |x, y| x + y) for Add. The result is a fresh TensorData; wrap it in Rc so the graph node and the returned Tensor share it.
  2. Decide whether to record history. Short-circuit when neither operand has history — no graph involvement, just return the data. Otherwise pick a shared graph (panic on a mismatch) and look up each operand's node id, registering a leaf for operands that didn't have one yet.
  3. Apply the op to the graph. Call graph.apply(TensorOp::Add, out_rc.clone(), vec![a_id, b_id]) to add a new node and get its id.
  4. Return the new Tensor with the data Rc and the freshly-built History.

Skeleton — fill in the body yourself:

impl Add<&Tensor> for &Tensor {
    type Output = Tensor;
    fn add(self, other: &Tensor) -> Tensor { todo!() }
}

Then add a Tensor + Tensor impl that just forwards to &Tensor + &Tensor, and you can write either a + b (consumes) or &a + &b (borrows). PyTorch lets you do both for the same reason. Once you have one binary op working, factor steps 1–4 into a make_binary_op_ref helper and have every overload delegate to it; the parent-id lookup deserves its own helper too (call it whatever — the in-tree code uses Tensor::node_id_in and pick_shared_graph).

Re-learning from module 1: the log_back nudge consistency bit us when training xor — gradients exploded near sigmoid saturation. Don't repeat it in Log's backward. Forward and backward must describe the same function.

Small helpers that emerge while implementing the table

You'll find yourself reaching for these — define them when you do rather than upfront:

  • TensorData::contiguous(&self) -> Self — materializes a row-major copy. View backward needs it because the upstream gradient might be a strided view (e.g. produced by an earlier Permute's backward), and a no-copy reshape on strided storage walks values in the wrong order. Whenever you need contiguous values from a possibly-strided tensor, this is the one-liner.
  • TensorData::permute_last_two(&self) -> Self — transpose of the trailing two dims (batch dims untouched). The MatMul backward formula d @ B^T and A^T @ d needs exactly this. Just a permute with axes [0, 1, ..., n-1, n-2].
  • TensorGraph::clear_gradients(&mut self) — wipe every node's gradient back to None. Call this at the top of Tensor::backward so calling it twice produces the same result both times (without it, intermediate nodes are read as upstream on the second pass and you over-accumulate). The standard PyTorch tradeoff between leaf-accumulation-as-feature and intermediate-resets does not apply here — clear everything, every time, and add a flag later if you actually want gradient accumulation across mini-batches.

Three traps worth flagging now

Matmul backward: why d @ b.T and a.T @ d?

For C = A @ B with A: (m, k) and B: (k, n), output C: (m, n). Pick a single element C[i, j] = Σ_k A[i, k] * B[k, j]. Differentiate w.r.t. A[i, k]: ∂C[i, j]/∂A[i, k] = B[k, j]. So with upstream grad d shaped (m, n):

grad_A[i, k] = Σ_j d[i, j] * B[k, j] = (d @ B.T)[i, k]

And symmetrically for B: grad_B = A.T @ d. That's the whole derivation. The transpose comes from the dimension that gets "summed out" being different on each side.

Broadcasting backward: why the reduce-sum?

If a: (3,) and b: (4, 3), then c = a + b has shape (4, 3). The upstream gradient d also has shape (4, 3). But a's gradient must have shape (3,) — same as a. Each element of a contributed to 4 rows of c, so its gradient is the sum of those 4 rows:

grad_a = d.sum(dim=0)  // → shape (3,)

This is why the Broadcast op stores the original shape: backward needs to know which dims to sum over.

Sum backward: why the broadcast?

Exact inverse of broadcast-backward. If c = a.sum(dim=0) where a: (4, 3) and c: (3,), upstream d has shape (3,). Each element of a contributed once to the corresponding element of c, so:

grad_a = broadcast(d, orig_shape=(4, 3))

Same stride-0 trick we use in the forward broadcast — no actual data copying needed for the gradient tensor.

Tests

  • Forward correctness. Each op with hand-computed expected outputs on tiny tensors.
  • Backward correctness via central_difference. Lift the scalar central_difference to tensors — perturb one element of an input at a time, compute (loss(+ε) - loss(-ε)) / 2ε, compare to autograd. This is the load-bearing test — if autograd matches numerical gradient for every op, you're done.
  • Broadcasting gradient. (a: shape [3]) + (b: shape [4, 3]): verify grad_a is reduced to shape [3].
  • Matmul gradient. a: [2, 3], b: [3, 4]: verify grads against central_difference.

6. Backward through tensor ops

Tensor::backward() is the same algorithm as the scalar version, lifted to tensors. The driver is a five-step routine on TensorGraph (or Tensor, with a thin wrapper):

  1. Clear leftover gradients. Walk every node, set gradient = None. Without this, calling backward() twice in a row over-accumulates because intermediate nodes are read as upstream on the second pass.
  2. Seed the root. Set the calling tensor's gradient to TensorData::ones(shape) — the multivariable equivalent of ∂loss/∂loss = 1.
  3. Topo sort. Reuse the DFS from scalar::autodiff; the algorithm is unchanged.
  4. Walk in reverse. For each node, ask it for its parent-id-to-gradient pairs (one op-specific routine per TensorOp variant — see §5).
  5. Accumulate into each parent. If the parent had no gradient yet, assign; otherwise zip(+) the new contribution onto the old. This is correct for shared parents (multivariable chain rule sums over usage sites).

Two things "seeded with ones" is doing implicitly. First, the loss tensor is assumed to be scalar-shaped (or you've at least .sum()d it down). Second, the seed is what makes the gradients computed everywhere downstream actually mean ∂loss/∂x — without it you'd be propagating zeros and getting zero gradients everywhere. If you ever want a non-scalar "vector-Jacobian product" backward (PyTorch's backward(gradient=...)), you'd accept a seed argument instead of materializing ones.

Skeleton — fill in the body yourself by translating the five steps:

}
Forward (solid) and backward (dashed red) for loss = (x @ w + b).sigmoid().bce(t). Backward traverses the same DAG in reverse, applying each op's backward rule to deposit gradients on its parents.

The only structural difference from scalar backward is that gradients themselves are tensors (matching the output shape of each node) instead of scalars. Accumulation uses tensor add; the broadcast-backward trick (sum over broadcast dims) is what reconciles a downstream gradient that's been broadcast back to its original input shape.

Tensor BCE

pub fn bce(pred: &Tensor, target: &Tensor) -> Tensor {
    let ones_t = Tensor::from_data(TensorData::ones(target.shape().to_vec()));
    let ones_p = Tensor::from_data(TensorData::ones(pred.shape().to_vec()));
    -&(target * &pred.log() + &(&ones_t - target) * &(&ones_p - pred).log())
}

TensorLinear:

pub struct TensorLinear {
    pub weights: Tensor,  // shape: [in_size, out_size], requires_grad
    pub biases:  Tensor,  // shape: [out_size], requires_grad, broadcasts on forward
}

impl TensorLinear {
    pub fn new(in_size: usize, out_size: usize) -> Self { /* Xavier */ }
    pub fn forward(&self, x: &Tensor) -> Tensor {
        x.matmul(&self.weights) + &self.biases
    }
}

Notice weights and biases ARE tensors with requires_grad, not raw Vec<Vec<f64>>. That solves the parameter-vs-NodeId impedance mismatch from module 1 (no separate weight_ids: Option<Vec<Vec<NodeId>>> field needed — the tensor IS the graph node).

The training loop:

for epoch in 0..epochs {
    for (x_vec, label) in shuffled(&dataset) {
        let x = Tensor::from_data(TensorData::new(x_vec, vec![1, 2]));
        let target = Tensor::from_data(TensorData::new(vec![label], vec![]));
        let pred = network.forward(&x);
        let loss = bce(&pred, &target);
        loss.backward();
        network.step(lr);
    }
}

No explicit graph anywhere in user code. The graph is created on-demand when ops happen, lives across the forward + backward + step, and drops when the tensors do. network.step walks all requires_grad tensors via the same Module::children machinery and does w.data -= lr * w.grad per parameter.
